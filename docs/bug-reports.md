# 缺陷记录（Jira 风格，自建流程）

> 说明：项目是个人项目，没有 Jira/禅道。这里是按 bug 单的字段写的真实缺陷记录——都是我写这个项目时**真的踩到并修掉**的问题，附根因与回归用例。面试可以直接按单子讲。

## BUG-001 · 丢帧时"超时"永远不触发

| 字段 | 内容 |
|---|---|
| 严重级别 | 严重（可靠性计数失真） |
| 发现方式 | 注入丢帧（`SIM_FAULT=drop`）后看统计：超时始终为 0，正常帧数却对不上 |
| 环境 | Windows 11 · Qt 6.8.3 · 周期 100 ms、超时 250 ms |
| 复现步骤 | 1) 起模拟样机 `SIM_FAULT=drop`；2) `hmi_app --smoke --seconds 8 --interval 100`；3) 观察 `timeouts` 与 `ok_frames` |
| 期望 | 丢帧应被计为超时并触发重试 |
| 实际 | `timeouts=0`，迟到应答还会被算到下一次请求上（数据错配） |
| 根因 | 没有"在途请求槽"：100 ms 周期 + 250 ms 超时时，请求还没回来就发下一个；超时定时器每次都被新请求重置，永远等不到触发 |
| 修复 | 加 `m_inFlight`：同一时刻只允许一个请求在途；超时/应答到达才释放 |
| 回归 | `test_dropped_frames_become_timeouts_not_lost`（pytest）断言超时>0、重试=超时、成功+超时≤节拍 |

## BUG-002 · 采集链进线程后，启动先卡 3.5 s 才出第一帧

| 字段 | 内容 |
|---|---|
| 严重级别 | 中（性能/启动体验，也会让短时冒烟少采 40% 数据） |
| 发现方式 | 重构后冒烟帧数从 79 掉到 44；对比 CSV 时间戳发现首帧晚了 3.5 s |
| 环境 | Windows 11 · Qt 6.8.3 · 8 s / 100 ms |
| 复现步骤 | 起样机后跑 `--smoke --seconds 8 --interval 100`，看 CSV 首行时间与进程启动时间的差 |
| 期望 | 首帧 < 1 s |
| 实际 | 首帧 ≈ 3.6 s |
| 根因 | `QTimer` 在构造函数里创建、对象随后 `moveToThread` —— 定时器仍归属旧线程，`start()` 报 "Timers cannot be started from another thread" 且永不触发；于是连接探测一直失败，等 3 s 连接超时 + 0.5 s 退避后第二次 `open()` 才成功 |
| 修复 | 定时器改为在目标线程里就地创建（`IoWorker::open()`、`PollEngine::start()`） |
| 回归 | `test_first_frame_within_two_seconds`（pytest）+ CI 冒烟门槛提到 70 帧（原 bug 会得 44，直接红） |

## BUG-003 · 界面卡顿导致采集节拍减半

| 字段 | 内容 |
|---|---|
| 严重级别 | 中（性能缺陷） |
| 发现方式 | 加 `--ui-load` 模拟界面压力后对比帧数 |
| 环境 | Windows 11 · 周期 100 ms · UI 线程每 100 ms 忙等 200 ms |
| 复现步骤 | `hmi_app --smoke --seconds 6 --interval 100 --ui-load 200` |
| 期望 | 采集节拍不受 UI 影响（≈10 Hz） |
| 实际 | 第一版（采集全在 UI 线程）6 s 只采到 31 帧；只搬传输层后仍降到 5 Hz 附近 |
| 根因 | 轮询定时器与解析都在 UI 线程，界面一忙就把节拍拖慢 |
| 修复 | 把 `PollEngine`（轮询/解析）与 `IoWorker`（收发）放进同一条 I/O 线程，UI 只做显示与落盘 |
| 回归 | `test_ui_load_does_not_starve_sampling`，断言 UI 饱和下帧数 ≥ 70% 理论值 |

---

### 我在这套记录里形成的习惯

1. **先能复现再动手**：三个 bug 都是先用注入/压力手段稳定复现（丢帧、坏 CRC、UI 忙等），不是"改完试试看"。
2. **修完立刻写回归**：每条修复都对应一个 pytest 或 QtTest 用例，CI 里跑。
3. **单子里写清"怎么发现的"**：面试问"你最有成就感的 bug"时，这三条都能讲成完整故事：现象 → 复现 → 根因 → 修复 → 防回归。
